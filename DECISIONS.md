# DECISIONS.md

Assumptions and choices made where `spec.md` is ambiguous or silent, plus every library or feature
added beyond the spec. Spec section 12 decisions are authoritative and are not repeated here.

| # | Slice | Topic | Decision | Why |
|---|---|---|---|---|
| D1 | 1.1 | Spring Boot version | **3.5.16**, the newest 3.x release. Boot 4.x exists but the spec pins 3.x. Companions: Spring Modulith 1.4.13, springdoc 2.9.1 (built against Boot 3.5.16), Testcontainers 1.21.4 (Boot-managed). | Spec section 2. |
| D2 | 1.1 | JDK | Sources compile with `--release 21` and **all compilation and tests run on JDK 21** through Maven Toolchains (D19). | D3 | 1.1 | MinIO image | `minio/minio` and `minio/mc` are no longer published on Docker Hub or quay.io (pulls fail). This keeps the same software from a reachable registry. Swapping it back later is a one-line change. |
| D4 | 1.1 | kafka-ui image | `ghcr.io/kafbat/kafka-ui:v1.3.0`, the maintained fork of `provectuslabs/kafka-ui`, which is unmaintained. | Same product, maintained. |
| D5 | 1.1 | Bucket-init healthcheck | The one-shot `minio-init` container has no healthcheck because it exits after creating buckets. Dependents use `condition: service_completed_successfully`, which is the equivalent readiness signal. Every long-running service has a healthcheck. | A healthcheck on an exited container is meaningless. |
| D6 | 1.1 | Table ownership | One Postgres database, `public` schema. Each table is owned by one context (see the table below). Cross-context references are UUID columns **without** foreign keys. | Simplest option. Spring Modulith enforces code-level access, and no FKs keeps contexts independently evolvable. |
| D7 | 1.1 | Base path | Controllers use `@RequestMapping(ApiPaths.V1 + "/...")` rather than a servlet context path, so `/actuator/**` and `/.well-known/jwks.json` stay at the root. | Spec 5 and 6. |
| D8 | 1.1 | UUIDv7 | Own small generator, `com.cadence.events.UuidV7` (RFC 9562, monotonic within a millisecond), instead of a library. It lives in `cadence-events` because the transcoder also mints event IDs. Hibernate 6.6 has no v7 style. Entities assign IDs in their constructors. | Avoids an extra dependency. |
| D9 | 1.1 | Outbox | Table `outbox_event` written via `OutboxWriter` (`Propagation.MANDATORY`, so it can only join an existing transaction). `OutboxPoller` runs every 500 ms (`CADENCE_OUTBOX_POLL_INTERVAL`), claims up to 100 rows with `FOR UPDATE SKIP LOCKED` in creation order, sends each synchronously to Kafka, marks `published_at`, and stops the batch at the first failure to keep per-key order. Published rows are purged after 7 days. Kafka record value is the envelope JSON (String serde). Delivery is at-least-once, which is why consumers are idempotent. | Spec 3.4 offers "outbox table + poller or Debezium". The poller is simpler. |
| D10 | 1.1 | Processed events | Table `processed_event(consumer, event_id)` with `ProcessedEvents.markProcessed(consumer, eventId)` → `INSERT … ON CONFLICT DO NOTHING`, called in the consumer's transaction. | Idempotent consumers (spec 3.4). |
| D11 | 1.1 | Problem details | `type` = `https://cadence.dev/problems/{code}` (an identifier, not a resolvable URL). Every problem also carries a machine-readable `code` property. Validation errors add an `errors: [{field, message}]` array. Unexpected 500s never leak exception messages. | RFC 7807. |
| D12 | 1.1 | Cursor format | Opaque base64url of a small JSON array of sort-key values (e.g. `[createdAt, id]`). Page size `limit` defaults to 20 and is clamped to 1..100. A malformed cursor returns a 400 problem. | Spec 5 says only `?limit&cursor`. |
| D13 | 1.1 | Event envelope | `EventEnvelope.payload` is a Jackson `JsonNode`, so one record serves every event type and the recommender. Typed payload records convert with `payloadAs(...)`. A JSON Schema for the envelope ships in `cadence-events` (`schemas/event-envelope.schema.json`). `cadence-events` auto-configures the shared Jackson settings (ISO-8601 instants, ignore unknown properties) for both apps. | Spec 3.1 and 3.5. |
| D14 | 1.1 | Config loading | Apps read `.env` via `spring.config.import: optional:file:.env[.properties]` (repo root and module directory), so `./mvnw spring-boot:run` works with the same `.env` as Compose. Secrets have no defaults in `application.yml`. | Single source of local config, no committed secrets. |
| D15 | 1.1 | Test split | `*Test` = unit tests (surefire). `*IT` = Testcontainers integration tests (failsafe). Both run in `./mvnw verify`. | Standard Maven split. |
| D16 | 1.1 | Awaitility (test only) | Added `org.awaitility:awaitility` (version managed by the Boot BOM) for asynchronous assertions on Kafka/outbox delivery. | Avoids hand-written sleep/poll loops in event-driven tests. |
| D17 | 1.1 | Infra ports and auth | Compose binds every port to `127.0.0.1` only. Redis requires a password (`REDIS_PASSWORD`). `make up` waits for the long-running services (`--wait`), then runs `minio-init` in the foreground, because `--wait` reports a finished one-shot container as a failure. | Local-only (spec 12 #4), no secrets in code. |
| D18 | 1.1 | Event payload equality | `EventEnvelope.create` builds the payload by serializing and re-parsing, not with `valueToTree`, so a freshly created envelope `equals()` its Kafka round-tripped copy (numeric node types match). | Makes dedupe and test comparisons reliable. |
| D19 | 1.2 | JDK selection | `maven-toolchains-plugin:select-jdk-toolchain` with `version [21,22)` in the parent POM, so `./mvnw` compiles, tests and `spring-boot:run`s on JDK 21 whatever shell or `JAVA_HOME` it starts from. Auto-discovery doesn't find Homebrew's keg-only `openjdk@21`, so `scripts/setup-toolchains.sh` (`make toolchains`) writes `~/.m2/toolchains.xml` once per machine; it never overwrites an existing file. `.envrc` (direnv) exports `JAVA_HOME` for JDK 21. Both version-check candidates, because `/usr/libexec/java_home -v 21` returns any JDK ≥ 21 (it returned 26 here). | User request; per-machine paths stay out of the repo. |
| D20 | 1.2 | Refresh tokens | Opaque 256-bit random values; only the SHA-256 hex is stored. `refresh_tokens` adds `family_id` and `created_at` to the spec 4 fields: every login starts a family, and rotation keeps it. Refresh locks the row (`PESSIMISTIC_WRITE`). Presenting a token that already has a successor (`replaced_by`) revokes the whole family, and that revocation commits even though the call returns 401 (`noRollbackFor`). Two concurrent refreshes of the same token therefore count as reuse. The 30-day TTL restarts on each rotation. Logout revokes the token's family and is idempotent (204 for unknown tokens). | Spec 6 says "reuse revokes the family" but doesn't define a family. |
| D21 | 1.2 | Access-token claims | `iss=cadence`, `sub=userId`, `roles` (e.g. `["LISTENER"]`), `plan`, `token_use=access`, `iat`/`exp` (15 min). No email or PII. All Cadence JWTs share one key, so every decoder also checks `token_use`; a playback-URL token can never authenticate API calls. | Defense in depth for one signing key. |
| D22 | 1.2 | JWT keys | PEM files: PKCS#8 private and X.509 public, at `CADENCE_JWT_PRIVATE_KEY_LOCATION` and `CADENCE_JWT_PUBLIC_KEY_LOCATION`. `make keys` (`scripts/generate-dev-keys.sh`) writes them to the git-ignored `secrets/`. Startup fails if the files are missing or not a pair. `kid` = RFC 7638 thumbprint. `spring-boot:run` uses the repo root as working directory, so relative `file:secrets/...` and `.env` resolve the same way everywhere. Tests generate a throwaway pair at runtime. | Spec 6: RS256, key from config, no committed private keys. |
| D23 | 1.2 | Login rate limit | Bucket4j on Redis (Lettuce CAS proxy manager), capacity 5 refilled all at once every minute (`refillIntervally`, so "5 per minute" holds exactly and tests are deterministic), keyed by client IP. The client IP is `getRemoteAddr()` with `server.forward-headers-strategy=native`, so `X-Forwarded-For` is honoured only from loopback or private-range proxies (the Vite proxy in Phase 2). Every attempt counts, successful or not. The limiter **fails open** with a warning if Redis is down. 429 responses carry `Retry-After`. | Spec 6; availability over strictness for a local app. |
| D24 | 1.2 | Password and email rules | Passwords: at least 10 characters and at most 72 UTF-8 bytes, because BCrypt ignores anything longer (400 `weak-password` / `password-too-long`). Emails are trimmed and lower-cased before storage and lookup, so they are unique case-insensitively. Login runs BCrypt against a dummy hash for unknown emails, so response timing doesn't reveal which emails are registered, and both cases return the same 401 `invalid-credentials`. | Spec 6 plus standard hardening. |
| D25 | 1.2 | Problem codes (auth) | `unauthorized` (no token), `invalid-token` (bad, expired or wrong-use token, with `WWW-Authenticate: Bearer error="invalid_token"`), `forbidden`, `invalid-credentials`, `invalid-refresh-token`, `refresh-token-reused`, `email-taken`, `rate-limited`, `validation-failed`. | Machine-readable errors for the web client. |
| D26 | 1.2 | Plan changes | No HTTP endpoint changes a plan; Premium is only a flag (spec 1 non-goals). Other contexts read the plan through the public `identity.UserAccounts` API (`planOf`), and tests/tools call `UserAccounts.changePlan`. `PATCH /me` changes only displayName, avatarUrl and country (spec 5). | Stays within the spec. |
| D27 | 1.2 | Admin bootstrap | At startup, if `CADENCE_ADMIN_EMAIL` and `CADENCE_ADMIN_PASSWORD` are set and the email isn't registered, create a user with roles ADMIN and LISTENER. An existing user is never modified, and a password change in `.env` is not applied. Concurrent instances are safe because of the unique email constraint. | Spec 4. |
| D28 | 1.3 | Object keys | Keys follow the spec literally, even though each prefix also has its own bucket: `raw/{trackId}/source.{ext}` in `cadence-raw` and `hls/{trackId}/...` in `cadence-hls`. | Spec 3.3. |
| D29 | 1.3 | Upload limits | `upload-url` requires `extension` (mp3/flac/wav/m4a) and `sizeBytes` (≤ 200 MB). The presigned PUT (15 min) **signs `Content-Type` and `Content-Length`**, so storage itself rejects any other size; a test proves this. `upload-complete` re-checks the size and sniffs magic bytes (ID3/MPEG sync, `fLaC`, `RIFF…WAVE`, `ftyp`). That is the "MIME check"; on failure the object is deleted and the API returns 400 `invalid-audio`. | Spec 6: 200 MB, MIME-checked. |
| D30 | 1.3 | Storage credentials | `minio-init` creates a least-privilege user (`CADENCE_S3_ACCESS_KEY`) with Get/Put/Delete/List on the two buckets only; root credentials are used only by `minio-init`. Presigned URLs are signed against `CADENCE_S3_PUBLIC_ENDPOINT` (what the browser reaches), while the API talks to `CADENCE_S3_ENDPOINT`. All code uses the plain S3 API (AWS SDK v2, path-style), so the MinIO image is swappable (per the user's instruction). | Least privilege; containerised API in 1.4. |
| D31 | 1.3 | Public catalog | Catalog GETs need no authentication. Listeners only ever see READY tracks: artist top tracks and album tracklists filter on READY, and `GET /tracks/{id}` returns 404 for any other status. Admins see every status via `/admin/tracks`. | Spec 4: a track is playable only when READY. |
| D32 | 1.3 | `catalog.entity-changed` | Emitted from 1.3, not 2.1, on every create, update, delete and status change of artists, albums and tracks, keyed by entity id. Payload is `{action: CREATED/UPDATED/DELETED, snapshot}`, where the snapshot is the public read model (`ArtistView`, `AlbumView`, `TrackSummary`) or null on delete. Search and the recommender need no call-back. | Spec 3.4 / Phase 2 prompt; avoids reworking every write later. |
| D33 | 1.3 | Genres | The spec has no genre write endpoints. Genres are created implicitly by name in album create/patch, de-duplicated case-insensitively (unique index on `lower(name)`). `GET /genres` is alphabetical and cursor-paginated. | Simplest consistent option. |
| D34 | 1.3 | Catalog writes | PATCH bodies: `null` = unchanged, empty string clears an optional text field. Deleting an artist that has albums or track credits is 409 `artist-in-use`; deleting an album with tracks is 409 `album-has-tracks`. Deleting a track also removes its raw and HLS objects after commit (best effort). A track without explicit credits gets the album artist as PRIMARY; every track needs a PRIMARY artist. Creates are not idempotent (documented in OpenAPI); PATCH, DELETE and the upload steps are. | Spec 11. |
| D35 | 1.3 | Extra admin endpoint | Added `GET /admin/tracks/{id}`, which returns a track in any status with processing details, for upload UIs and the seed script to poll. | Small addition, not in spec 5. |
| D36 | 1.3 | Transcode jobs | The `catalog.track-uploaded` event id is the transcode job id, stored on the track (`transcode_job_id`). Results from any other job are ignored, so a stale retry can't overwrite a newer upload. `upload-complete` is idempotent while PROCESSING (no second job); `retranscode` is allowed only from FAILED (409 `track-not-failed`); a new `upload-url` is refused while PROCESSING (409 `track-processing`). | Correct, idempotent async processing. |
| D37 | 1.3 | HTTP client gotcha | The AWS SDK's default `apache5-client` puts Apache HttpClient 5 on the classpath, and Spring then auto-selects it for `RestTemplate`/`RestClient`. Its default retry strategy **silently waits out `Retry-After` and retries 429/503**. Tests pin the JDK client. The Phase 3 `RecommenderClient` must configure its client and retries explicitly. | Found when the login rate-limit test passed only after a 60 s hidden retry. |
| D38 | 1.4 | Manifest URLs and expiry | `POST /playback/{id}` returns an API URL for the master playlist carrying a signed playback JWT (`token_use=playback`, `scp=master`, `trk`, `mbr` max kbps, `dur`), valid **5 minutes** (`expiresAt`). The served master's variant URIs are relative (`160k/index.m3u8?token=…`) with a `scp=media` token. Variant playlists rewrite segment URIs to presigned MinIO GETs, so audio bytes still go straight from storage to the player. **Deviation:** media tokens and presigned segment URLs live 5 min **+ the track duration**, not a flat 5 min. hls.js loads a VOD playlist once, so flat 5-minute URLs would break seeking or playback past minute 5 of longer tracks. The entry URL keeps the 5-minute limit. | Spec 3.2 vs real hls.js behaviour. |
| D39 | 1.4 | Premium bitrate rule | The plan is read from identity (`UserAccounts.planOf`) at playback start rather than from the access-token claim, so upgrades apply immediately. FREE: the master lists 96k and 160k only, and fetching `320k/index.m3u8` with a free grant returns 403 `bitrate-not-allowed`. PREMIUM: all three. | Spec 4: free max 160 kbps. |
| D40 | 1.4 | Range fallback | `GET /tracks/{id}/stream` (bearer auth, READY only) serves `hls/{id}/fallback_160k.m4a`, a single-file 160 kbps AAC (faststart MP4) written in the same FFmpeg pass. It supports `bytes=a-b`, `bytes=a-` and `bytes=-n`. Malformed, multi-range or unsatisfiable headers return **416** with `Content-Range: bytes */size`; RFC 9110 would allow ignoring a malformed header, but the task asks for "invalid → 416". | Spec 5, user test spec. |
| D41 | 1.4 | Transcoder design | `ffprobe` for the audio stream and duration. One FFmpeg pass: `var_stream_map` for 3 AAC renditions (44.1 kHz stereo, mono upmixed), 10 s MPEG-TS segments, `master.m3u8`, and the fallback file. A second pass runs `ebur128` for integrated loudness (null if it can't be measured). The transcoder owns no DB, so it publishes results directly to Kafka **after** the output is stored. Idempotency comes from `result.json` (job id), written last; a redelivered job republishes it without re-running FFmpeg. The output prefix is cleared before upload. Concurrency 1, `max.poll.records=1`, 15 min poll interval, 10 min FFmpeg timeout (`CADENCE_TRANSCODE_TIMEOUT`). Bad input or FFmpeg errors become `-failed` immediately; infrastructure errors are retried 3 × 5 s and then reported as `-failed` so tracks never stay PROCESSING. | Spec 3.3; 10 s tone transcodes in under 1 s. |
| D42 | 1.4 | Loudness | Stored on the track (`loudness_lufs`) for future volume normalization; not exposed in public APIs yet. | Spec 3.3 asks to extract it. |
| D43 | 1.4 | Containers | Multi-stage Dockerfiles: the `maven:3.9-eclipse-temurin-21` build registers its JDK in the global `toolchains.xml`; the runtime is `eclipse-temurin:21-jre` plus `curl` (and `ffmpeg` for the transcoder), non-root uid 10001, healthcheck on `/actuator/health/liveness`. Compose profile `app` (`make app`) runs both on `cadence-net` with in-network addresses overriding `.env`. The API container runs with the `dev` profile by default (`CADENCE_API_PROFILES`) and mounts `secrets/` read-only. | Spec 8. |
| D44 | 1.4 | Dev player | `/dev/player.html` is served only with the `dev` profile (it isn't under `static/`). It uses hls.js 1.6.13 from jsDelivr. Track selection lists READY tracks via the admin endpoint (when logged in as admin) or takes a pasted track id. | Spec 12 #3. |
| D45 | 1.4 | API Kafka consumers | One consumer group per context (`cadence-api.catalog`, …). Errors are retried 3 × 1 s, then logged and skipped; malformed envelopes are skipped immediately. Consumers dedupe through `processed_event` in the same transaction as their effect. | Spec 3.4. |
| D46 | 1.5 | Playlist ordering | `playlist_tracks.position` is a fractional-index key (`FractionalIndex`, a port of the `fractional-indexing` algorithm, base 62) stored `COLLATE "C"` so SQL order equals Java string order, and unique per playlist. Inserting or moving writes only the affected rows; appends stay ≤ 4 characters for 10,000 tracks. A track appears at most once in a playlist (re-adding is skipped), because reorder addresses tracks by id (`{trackId, afterTrackId}`, spec 5). | Spec 4 "fractional/lexorank"; spec 5 reorder shape. |
| D47 | 1.5 | Playlist versioning | `version` (JPA `@Version`) bumps on every metadata **or** track change and is the ETag (`"7"`). `PATCH` requires `If-Match` (428 `precondition-required` when missing, 412 `version-mismatch` when stale). Add, remove and reorder accept an optional `If-Match`. Track changes flush the version-checked playlist row **before** touching track rows, so concurrent edits serialize on that row: the loser gets 409 `concurrent-modification` (or 412 if it sent `If-Match`) and no write is lost (tested with 8 parallel adds). Phase 3 adds the automatic retry. | Spec 5, spec 9 Phase 3. |
| D48 | 1.5 | Playlist access | New playlists default to **PRIVATE**. Private playlists are 404 to everyone but the owner; public ones are readable by any authenticated user. Only the owner can change or delete (403 for others who can see it). The `collaborative` flag is stored now; collaborator editing comes in Phase 3. | Privacy by default; spec 6 domain checks. |
| D49 | 1.5 | `/me/playlists` | Returns the caller's own playlists, newest first. Spec 5 says "own + followed", but the spec has no follow-playlist endpoint or entity, so there is nothing to follow yet. Collaborative playlists will be included in Phase 3. | Simplest consistent option. |
| D50 | 1.5 | Track availability | Only READY tracks can be added to playlists (400 `unknown-track`) or liked (404). Tracks that later leave READY stay in playlists and are returned with `playable=false`, or with `track: null` if deleted. | Spec 4: only READY is playable. |
| D51 | 1.5 | Library events | `library.track-liked` carries `track-liked` and also `track-unliked`; `library.artist-followed` carries `artist-followed` and `artist-unfollowed`. Keyed by user id, in the shared envelope with `itemType` `song`/`artist` and an empty payload. Events fire only on an actual state change, so repeated PUT/DELETE calls emit nothing. Writes use `INSERT … ON CONFLICT DO NOTHING`, so races are harmless. | Recommender needs to retract signals; spec 3.4/3.5. |
| D52 | 1.5 | Saved albums | Spec 4 has the SavedAlbum entity but spec 5 lists no endpoint. Added the Spotify-style `PUT/DELETE /me/albums/{albumId}` and `GET /me/albums` (no events). | An unusable entity would be dead code. |
| D53 | 1.5 | Playlist size | At most 10,000 tracks: checked with a row count before inserting (409 `playlist-full`), backed by a CHECK constraint on `track_count`. At most 100 track ids per add/remove request. `position` is a 0-based index; values past the end append. | Spec 4. |
| D54 | 1.6 | Acceptance tests | New test-only module `cadence-e2e`, last in the reactor. It starts Postgres, Kafka, Redis and MinIO in Testcontainers and runs the **packaged** `cadence-api` and `cadence-transcoder` jars as separate JVM processes (toolchain JDK 21, command-line config, no `.env`, dev profile). `Phase1AcceptanceIT` then drives each spec 9 Phase 1 criterion over HTTP, Kafka and S3, using FFmpeg/ffprobe as a real HLS client for playback and seeking. Running only `-pl cadence-e2e` requires the jars to be built first. | Criterion "admin uploads an MP3 → READY in 60 s" needs both apps together. |
| D55 | 1.6 | Seed script | `make seed` runs `scripts/seed.py` (Python 3 standard library, no dependencies) against the running API and transcoder. It uses files in `seed-audio/` (git-ignored) or generates 20 distinct FFmpeg tones (two-note chords with tremolo and fades, 20–45 s) in all four upload formats. It creates 5 artists, 10 albums (with genres) and the tracks through the real presigned-upload flow, waits for READY, and creates a demo listener (`CADENCE_DEMO_*`). Spec 8's "50 CC-licensed FMA tracks" is replaced by generated audio (no downloads or licensing); your own files can go in `seed-audio/`. | Prompt slice 1.6 overrides spec 8. |
| D56 | 1.6 | Browser check | `scripts/verify-player.sh` opens `/dev/player.html` in headless Chrome (real time, via the DevTools endpoint) with an `#autotest&token=…&track=…` fragment. The page plays a READY track with hls.js, seeks to 60 % and reports PASS/FAIL in its title. The fragment keeps the token out of server logs. It isn't part of `./mvnw verify`, so the build doesn't depend on a desktop browser. | Spec 9 AC4 names an hls.js page. |
| D57 | 1.6 | Seed artist name | "The Beatles Revival" is the fixture for Phase 2's fuzzy-search criterion ("beatls"). | Spec 9 Phase 2 AC1. |
| D58 | 2.1 | Elasticsearch | **8.19.22** (latest 8.x) in Compose and Testcontainers with the Boot-managed `elasticsearch-java` 8.18 client (Boot's `spring.elasticsearch.*` auto-configuration, no Spring Data). Compose runs one node with basic auth over plain HTTP (`ELASTIC_PASSWORD`, bound to 127.0.0.1); tests disable security. The disk watermark check is off so a nearly full laptop disk can't make indices read-only. | Spec 2: "Elasticsearch 8". |
| D59 | 2.1 | Index design | The search context owns four indices (`<prefix>-artists/-albums/-tracks/-playlists`, one shard, no replicas, strict mappings in `resources/search/*.json`). Text fields use a `folding` analyzer (lowercase + ASCII folding) plus a `search_as_you_type` subfield. Albums embed the artist name and tracks embed artist names and album title/cover, so a hit renders without joins. Only READY tracks and PUBLIC playlists are indexed. | Spec 5 search shapes; spec 4 READY rule. |
| D60 | 2.1 | Query | Each type runs one `bool` query whose `should` clauses are a `bool_prefix` multi-match on the `search_as_you_type` fields (prefixes, ×2), a `fuzziness: AUTO` multi-match with `prefix_length 1` and `operator and` (typos: "beatls" → "Beatlz"), and an exact-phrase boost (×3). `/search` sends one `_msearch` for all requested types. `/search/suggest` is a single query over all four indices (artists boosted ×1.5) returning the best 8 as `{type, id, text, subtitle, imageUrl}`. | Spec 5: fuzzy, prefix, suggest under 100 ms. |
| D61 | 2.1 | Search API | `GET /search` needs authentication (the rate limit is per user). Results are grouped by type, and each group is a `CursorPage` whose cursor is an offset. A cursor is only accepted with exactly one type (400 `cursor-needs-single-type`), and paging stops at 1,000 results. `q` must be 1–100 characters (400 `invalid-query`); unknown types return 400 `invalid-search-type`. Track hits are hydrated from the catalog (live play counts; stale non-READY entries dropped). Other types come straight from the index; playlist owner names come from `UserAccounts.displayNames`. Elasticsearch down → 503 `search-unavailable`. | Spec 5/6. |
| D62 | 2.1 | Search rate limit | `cadence.rate-limits.search` = 30 per 1 s per user id, shared by search and suggest (spec 6 "search 30/s/user"), same Bucket4j/Redis limiter as login (fails open). | Spec 6. |
| D63 | 2.1 | Indexer consistency | The indexer consumes `catalog.entity-changed` and `library.playlist-changed` (group `cadence-api.search`, one thread). Writes are full-document upserts or deletes by entity id, so redelivery is harmless and per-entity order is guaranteed by the key. Because Elasticsearch can't join the Postgres transaction, this consumer is idempotent by construction rather than through `processed_event`. Denormalized names converge in both arrival orders: when indexing a track or album the current artist/album documents are read with real-time GETs, and when an artist or album is renamed the embedding documents are rewritten with `update_by_query` (after an explicit refresh). Failures are retried indefinitely with back-off up to 30 s (not skipped as in D45): a skipped change would leave the index stale. | Spec 9 AC2: edits visible within 5 s. |
| D64 | 2.1 | Filling new indices | Whenever the indices have to be created (first start, wiped Elasticsearch, `POST /admin/search/reindex`), the search context asks the catalog (`CatalogReplay`) and the library (`PlaylistReplay`) to write UPDATED events for every entity to the outbox. The index is filled through the normal event path; there is no second bulk-load code path, and the recommender can use the same replay in Phase 3. | Existing data must become searchable without relying on Kafka retention. |
| D65 | 2.1 | `library.playlist-changed` | New topic (not in spec 3.4) carrying `EntityChangedPayload` with the `PlaylistView` snapshot on playlist create, update and delete. Keyed by **playlist id** (not user id) so one playlist's changes stay ordered. | Spec 5 lists `playlist` as a search type, and the library owns playlists, so search must learn about them from events. |
| D66 | 2.1 | Catalog cache | Spring Cache on Redis: `GET /artists/{id}` and `GET /albums/{id}` are cached for 10 minutes as typed JSON (keys `cadence:catalog.artist::{id}`, `cadence:catalog.album::{id}`). Every catalog change (all of them go through `CatalogEvents.entityChanged`) clears **both** caches after its transaction commits: pages embed each other's names, and admin writes are rare.

# DECISIONS.md

Assumptions and choices made where `spec.md` is ambiguous or silent, plus every library or feature
added beyond the spec. Spec section 12 decisions are authoritative and are not repeated here.

| # | Slice | Topic | Decision | Why |
|---|---|---|---|---|
| D1 | 1.1 | Spring Boot version | **3.5.16**, the newest 3.x release. Boot 4.x exists but the spec pins 3.x. Companions: Spring Modulith 1.4.13, springdoc 2.9.1 (built against Boot 3.5.16), Testcontainers 1.21.4 (Boot-managed). | Spec section 2. |
| D2 | 1.1 | JDK | Sources compile with `--release 21` and **all compilation and tests run on JDK 21** through Maven Toolchains (D19). Maven itself may run on any newer JDK; the machine default is 26/27. *(Amended in 1.2: the original `requireJavaVersion [21,22)` enforcer rule was replaced by toolchains.)* | Reproducibility. Mockito/ByteBuddy and Spring Boot 3.5 don't officially support JDK 26+. |
| D3 | 1.1 | MinIO image | `minio/minio` and `minio/mc` are no longer published on Docker Hub or quay.io (pulls fail). Compose and Testcontainers use the community rebuild **`pgsty/minio:RELEASE.2026-08-04T00-00-00Z`**: the same MinIO server and S3 API, and it ships `mc`. | Spec says MinIO. This keeps the same software from a reachable registry. Swapping it back later is a one-line change. |
| D4 | 1.1 | kafka-ui image | `ghcr.io/kafbat/kafka-ui:v1.3.0`, the maintained fork of `provectuslabs/kafka-ui`, which is unmaintained. | Same product, maintained. |
| D5 | 1.1 | Bucket-init healthcheck | The one-shot `minio-init` container has no healthcheck because it exits after creating buckets. Dependents use `condition: service_completed_successfully`, which is the equivalent readiness signal. Every long-running service has a healthcheck. | A healthcheck on an exited container is meaningless. |
| D6 | 1.1 | Table ownership | One Postgres database, `public` schema. Each table is owned by one context (see the table below). Cross-context references are UUID columns **without** foreign keys. | Simplest option. Spring Modulith enforces code-level access, and no FKs keeps contexts independently evolvable. |
| D7 | 1.1 | Base path | Controllers use `@RequestMapping(ApiPaths.V1 + "/...")` rather than a servlet context path, so `/actuator/**` and `/.well-known/jwks.json` stay at the root. | Spec 5 and 6. |
| D8 | 1.1 | UUIDv7 | Own small generator, `com.cadence.events.UuidV7` (RFC 9562, monotonic within a millisecond), instead of a library. It lives in `cadence-events` because the transcoder also mints event IDs. Hibernate 6.6 has no v7 style. Entities assign IDs in their constructors. | Avoids an extra dependency. |
| D9 | 1.1 | Outbox | Table `outbox_event` written via `OutboxWriter` (`Propagation.MANDATORY`, so it can only join an existing transaction). `OutboxPoller` runs every 500 ms (`CADENCE_OUTBOX_POLL_INTERVAL`), claims up to 100 rows with `FOR UPDATE SKIP LOCKED` in creation order, sends each synchronously to Kafka, marks `published_at`, and stops the batch at the first failure to keep per-key order. Published rows are purged after 7 days. Kafka record value is the envelope JSON (String serde). Delivery is at-least-once, which is why consumers are idempotent. | Spec 3.4 offers "outbox table + poller or Debezium". The poller is simpler. |
| D10 | 1.1 | Processed events | Table `processed_event(consumer, event_id)` with `ProcessedEvents.markProcessed(consumer, eventId)` → `INSERT … ON CONFLICT DO NOTHING`, called in the consumer's transaction. | Idempotent consumers (spec 3.4). |
| D11 | 1.1 | Problem details | `type` = `https://cadence.dev/problems/{code}` (an identifier, not a resolvable URL). Every problem also carries a machine-readable `code` property. Validation errors add an `errors: [{field, message}]` array. Unexpected 500s never leak exception messages. | RFC 7807. |
| D12 | 1.1 | Cursor format | Opaque base64url of a small JSON array of sort-key values (e.g. `[createdAt, id]`). Page size `limit` defaults to 20 and is clamped to 1..100. A malformed cursor returns a 400 problem. | Spec 5 says only `?limit&cursor`. |
| D13 | 1.1 | Event envelope | `EventEnvelope.payload` is a Jackson `JsonNode`, so one record serves every event type and the recommender. Typed payload records convert with `payloadAs(...)`. A JSON Schema for the envelope ships in `cadence-events` (`schemas/event-envelope.schema.json`). `cadence-events` auto-configures the shared Jackson settings (ISO-8601 instants, ignore unknown properties) for both apps. | Spec 3.1 and 3.5. |
| D14 | 1.1 | Config loading | Apps read `.env` via `spring.config.import: optional:file:.env[.properties]` (repo root and module directory), so `./mvnw spring-boot:run` works with the same `.env` as Compose. Secrets have no defaults in `application.yml`. | Single source of local config, no committed secrets. |
| D15 | 1.1 | Test split | `*Test` = unit tests (surefire). `*IT` = Testcontainers integration tests (failsafe). Both run in `./mvnw verify`. | Standard Maven split. |
| D16 | 1.1 | Awaitility (test only) | Added `org.awaitility:awaitility` (version managed by the Boot BOM) for asynchronous assertions on Kafka/outbox delivery. | Avoids hand-written sleep/poll loops in event-driven tests. |
| D17 | 1.1 | Infra ports and auth | Compose binds every port to `127.0.0.1` only. Redis requires a password (`REDIS_PASSWORD`). `make up` waits for the long-running services (`--wait`), then runs `minio-init` in the foreground, because `--wait` reports a finished one-shot container as a failure. | Local-only (spec 12 #4), no secrets in code. |
| D18 | 1.1 | Event payload equality | `EventEnvelope.create` builds the payload by serializing and re-parsing, not with `valueToTree`, so a freshly created envelope `equals()` its Kafka round-tripped copy (numeric node types match). | Makes dedupe and test comparisons reliable. |
| D19 | 1.2 | JDK selection | `maven-toolchains-plugin:select-jdk-toolchain` with `version [21,22)` in the parent POM, so `./mvnw` compiles, tests and `spring-boot:run`s on JDK 21 whatever shell or `JAVA_HOME` it starts from. Auto-discovery doesn't find Homebrew's keg-only `openjdk@21`, so `scripts/setup-toolchains.sh` (`make toolchains`) writes `~/.m2/toolchains.xml` once per machine; it never overwrites an existing file. `.envrc` (direnv) exports `JAVA_HOME` for JDK 21. Both version-check candidates, because `/usr/libexec/java_home -v 21` returns any JDK ≥ 21 (it returned 26 here). | User request; per-machine paths stay out of the repo. |
| D20 | 1.2 | Refresh tokens | Opaque 256-bit random values; only the SHA-256 hex is stored. `refresh_tokens` adds `family_id` and `created_at` to the spec 4 fields: every login starts a family, and rotation keeps it. Refresh locks the row (`PESSIMISTIC_WRITE`). Presenting a token that already has a successor (`replaced_by`) revokes the whole family, and that revocation commits even though the call returns 401 (`noRollbackFor`). Two concurrent refreshes of the same token therefore count as reuse. The 30-day TTL restarts on each rotation. Logout revokes the token's family and is idempotent (204 for unknown tokens). | Spec 6 says "reuse revokes the family" but doesn't define a family. |
| D21 | 1.2 | Access-token claims | `iss=cadence`, `sub=userId`, `roles` (e.g. `["LISTENER"]`), `plan`, `token_use=access`, `iat`/`exp` (15 min). No email or PII. All Cadence JWTs share one key, so every decoder also checks `token_use`; a playback-URL token can never authenticate API calls. | Defense in depth for one signing key. |
| D22 | 1.2 | JWT keys | PEM files: PKCS#8 private and X.509 public, at `CADENCE_JWT_PRIVATE_KEY_LOCATION` and `CADENCE_JWT_PUBLIC_KEY_LOCATION`. `make keys` (`scripts/generate-dev-keys.sh`) writes them to the git-ignored `secrets/`. Startup fails if the files are missing or not a pair. `kid` = RFC 7638 thumbprint. `spring-boot:run` uses the repo root as working directory, so relative `file:secrets/...` and `.env` resolve the same way everywhere. Tests generate a throwaway pair at runtime. | Spec 6: RS256, key from config, no committed private keys. |
| D23 | 1.2 | Login rate limit | Bucket4j on Redis (Lettuce CAS proxy manager), capacity 5 refilled all at once every minute (`refillIntervally`, so "5 per minute" holds exactly and tests are deterministic), keyed by client IP. The client IP is `getRemoteAddr()` with `server.forward-headers-strategy=native`, so `X-Forwarded-For` is honoured only from loopback or private-range proxies (the Vite proxy in Phase 2). Every attempt counts, successful or not. The limiter **fails open** with a warning if Redis is down. 429 responses carry `Retry-After`. | Spec 6; availability over strictness for a local app. |
| D24 | 1.2 | Password and email rules | Passwords: at least 10 characters and at most 72 UTF-8 bytes, because BCrypt ignores anything longer (400 `weak-password` / `password-too-long`). Emails are trimmed and lower-cased before storage and lookup, so they are unique case-insensitively. Login runs BCrypt against a dummy hash for unknown emails, so response timing doesn't reveal which emails are registered, and both cases return the same 401 `invalid-credentials`. | Spec 6 plus standard hardening. |
| D25 | 1.2 | Problem codes (auth) | `unauthorized` (no token), `invalid-token` (bad, expired or wrong-use token, with `WWW-Authenticate: Bearer error="invalid_token"`), `forbidden`, `invalid-credentials`, `invalid-refresh-token`, `refresh-token-reused`, `email-taken`, `rate-limited`, `validation-failed`. | Machine-readable errors for the web client. |
| D26 | 1.2 | Plan changes | No HTTP endpoint changes a plan; Premium is only a flag (spec 1 non-goals). Other contexts read the plan through the public `identity.UserAccounts` API (`planOf`), and tests/tools call `UserAccounts.changePlan`. `PATCH /me` changes only displayName, avatarUrl and country (spec 5). | Stays within the spec. |
| D27 | 1.2 | Admin bootstrap | At startup, if `CADENCE_ADMIN_EMAIL` and `CADENCE_ADMIN_PASSWORD` are set and the email isn't registered, create a user with roles ADMIN and LISTENER. An existing user is never modified, and a password change in `.env` is not applied. Concurrent instances are safe because of the unique email constraint. | Spec 4. |
| D28 | 1.3 | Object keys | Keys follow the spec literally, even though each prefix also has its own bucket: `raw/{trackId}/source.{ext}` in `cadence-raw` and `hls/{trackId}/...` in `cadence-hls`. | Spec 3.3. |
| D29 | 1.3 | Upload limits | `upload-url` requires `extension` (mp3/flac/wav/m4a) and `sizeBytes` (≤ 200 MB). The presigned PUT (15 min) **signs `Content-Type` and `Content-Length`**, so storage itself rejects any other size; a test proves this. `upload-complete` re-checks the size and sniffs magic bytes (ID3/MPEG sync, `fLaC`, `RIFF…WAVE`, `ftyp`). That is the "MIME check"; on failure the object is deleted and the API returns 400 `invalid-audio`. | Spec 6: 200 MB, MIME-checked. |
| D30 | 1.3 | Storage credentials | `minio-init` creates a least-privilege user (`CADENCE_S3_ACCESS_KEY`) with Get/Put/Delete/List on the two buckets only; root credentials are used only by `minio-init`. Presigned URLs are signed against `CADENCE_S3_PUBLIC_ENDPOINT` (what the browser reaches), while the API talks to `CADENCE_S3_ENDPOINT`. All code uses the plain S3 API (AWS SDK v2, path-style), so the MinIO image is swappable (per the user's instruction). | Least privilege; containerised API in 1.4. |
| D31 | 1.3 | Public catalog | Catalog GETs need no authentication. Listeners only ever see READY tracks: artist top tracks and album tracklists filter on READY, and `GET /tracks/{id}` returns 404 for any other status. Admins see every status via `/admin/tracks`. | Spec 4: a track is playable only when READY. |
| D32 | 1.3 | `catalog.entity-changed` | Emitted from 1.3, not 2.1, on every create, update, delete and status change of artists, albums and tracks, keyed by entity id. Payload is `{action: CREATED/UPDATED/DELETED, snapshot}`, where the snapshot is the public read model (`ArtistView`, `AlbumView`, `TrackSummary`) or null on delete. Search and the recommender need no call-back. | Spec 3.4 / Phase 2 prompt; avoids reworking every write later. |
| D33 | 1.3 | Genres | The spec has no genre write endpoints. Genres are created implicitly by name in album create/patch, de-duplicated case-insensitively (unique index on `lower(name)`). `GET /genres` is alphabetical and cursor-paginated. | Simplest consistent option. |
| D34 | 1.3 | Catalog writes | PATCH bodies: `null` = unchanged, empty string clears an optional text field. Deleting an artist that has albums or track credits is 409 `artist-in-use`; deleting an album with tracks is 409 `album-has-tracks`. Deleting a track also removes its raw and HLS objects after commit (best effort). A track without explicit credits gets the album artist as PRIMARY; every track needs a PRIMARY artist. Creates are not idempotent (documented in OpenAPI); PATCH, DELETE and the upload steps are. | Spec 11. |
| D35 | 1.3 | Extra admin endpoint | Added `GET /admin/tracks/{id}`, which returns a track in any status with processing details, for upload UIs and the seed script to poll. | Small addition, not in spec 5. |
| D36 | 1.3 | Transcode jobs | The `catalog.track-uploaded` event id is the transcode job id, stored on the track (`transcode_job_id`). Results from any other job are ignored, so a stale retry can't overwrite a newer upload. `upload-complete` is idempotent while PROCESSING (no second job); `retranscode` is allowed only from FAILED (409 `track-not-failed`); a new `upload-url` is refused while PROCESSING (409 `track-processing`). | Correct, idempotent async processing. |
| D37 | 1.3 | HTTP client gotcha | The AWS SDK's default `apache5-client` puts Apache HttpClient 5 on the classpath, and Spring then auto-selects it for `RestTemplate`/`RestClient`. Its default retry strategy **silently waits out `Retry-After` and retries 429/503**. Tests pin the JDK client. The Phase 3 `RecommenderClient` must configure its client and retries explicitly. | Found when the login rate-limit test passed only after a 60 s hidden retry. |
